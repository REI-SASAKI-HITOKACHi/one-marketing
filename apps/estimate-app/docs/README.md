# 見積作成Webアプリ 改修版（2026-09）

GPTからの引継ぎ資料（`estimate_app_handoff_2026-09-05`）を受けての改修。
依頼された2点に絞って対応した。

1. **読み込み／生成が遅すぎて実用に耐えない**
2. **変則的な割引を入れる機能がない**

請求書機能は今回の範囲外。ただし着手前提となるP0（マスタのスキーマ混在、
起動時マイグレーション、ヘッダー無視の書き込み）はこの改修で解消している。

---

## 0. 最初に読むべきこと：自動割引は現在まったく効いていない

調査中に、資料では「疑い」とされていた問題が**本番で確定**した。

`割引繁忙期マスタ` は旧ヘッダー（A列=ルールID, B列=有効…）のまま運用されているが、
旧コードの初期データ投入は**新スキーマの順番**（A列=有効, B列=ルールID…）でA列から書いていた。
その結果、`開始月` `終了月` `値` `条件` がすべて別の列を指していた。

読み取り側は `開始月`・`終了月` が数値であることを条件に月判定するため、**全ルールが不成立**になる。

| 機能 | 本番での実際の動き |
|---|---|
| 繁忙期の自動判定 | 常に「繁忙期ではない」 |
| 早期予約割引の自動判定 | 常に該当なし |
| 複数台割引 | 常に0円 |
| 「割引を適用」チェック | **入れても0円。何も起きない** |

つまり「変則的な割引を入れる機能がない」以前に、**通常の割引が1円も機能していなかった**。
既存の見積データでも `割引額` が全件0になっていることと一致する。

同じ原因で `メールテンプレートマスタ` も新列側が空のままで、
登録した文面ではなく**コード内のfallback文面**が使われていた。

さらに、旧コードは画面を開くたびに `setupInitialSheets()` を実行していたため、
既存判定に失敗した初期行が毎回追記され続けていた。

| シート | 本来の行数 | 現在の行数 |
|---|---|---|
| 割引繁忙期マスタ | 17 | **155** |
| メールテンプレートマスタ | 6 | **161** |

改修版は、**マスタを正規化する前でも列ずれ行を判別して正しく読む**ようにしてある。
デプロイ直後から自動判定は正しく動作する。

そのうえで、オーナーの選択に従い **`auto_discount_enabled` は初期値 `FALSE`** で納品する。
コードは直っているが金額は今のまま変わらない。現場に周知したうえで `TRUE` にすれば有効化される。

## 1. 遅さの原因と対策

### 実測できた主因

| # | 箇所 | 旧実装 | 影響 |
|---|---|---|---|
| 1 | `getMenus_()` | メニュー1件ごとに `pickMenuActiveValue_()` がシート全体を再読込。40メニューで**約80回**のシート読み込み | 初期表示の最大要因 |
| 2 | `apiInit()` | 毎回 `setupInitialSheets()`（9シートのヘッダー検査＋4種の初期データ投入）を実行 | 初期表示。マスタ増殖の原因でもある |
| 3 | `apiCalculateEstimate()` | **1文字入力するたび**にサーバーへ往復し、そのたび全マスタを読み直し（＝#1と#2を再実行） | 入力操作すべてが数秒待ち |
| 4 | `apiCreateEstimate()` | 冒頭でまた `setupInitialSheets()` | 見積作成 |
| 5 | 書き戻し | `updateEstimateFields_()` を2〜3回。毎回 設定読み直し＋スプレッドシートを開き直し＋203列のシートを検索 | 見積作成 |
| 6 | `log_()` | 1操作ごとにシートを開いて1行追記（1リクエストで4回） | 全体 |
| 7 | `writeDetailRows_()` | 明細を**1セルずつ64回** `setValue` | PDF生成 |
| 8 | `generateEstimateId_()` | 採番のために203列×全行を読み込み | 見積作成 |
| 9 | PDF生成 | 帳票/DBスプレッドシート（見積DB・請求DBを含む7シート）を丸ごと複製 | PDF生成。**データが増えるほど悪化** |
| 10 | PDF生成 | 固定の `Utilities.sleep(700)` | PDF生成 |

### 対策

| 対策 | 内容 |
|---|---|
| **計算をブラウザへ移した** | 計算エンジン `Calc.html` をクライアントとサーバーで共有。入力中のサーバー通信は**ゼロ**。保存時だけサーバーが同じ関数で再計算し、その結果を正とする |
| **マスタを1回だけ読んでキャッシュ** | 全マスタを1つのJSONにまとめ CacheService に6時間保持（100KB制限があるため分割保存）。2回目以降の初期表示はシートを読まない |
| **メニュー読み込みを1回に** | 同じ行から `有効` を読む。80回 → 1回 |
| **セットアップを起動パスから分離** | `Admin.gs` の管理者関数へ隔離。Webアプリからは呼ばない |
| **2フェーズ保存** | `apiSaveEstimate()`（保存のみ）→ `apiBuildDocuments()`（PDF・メール）。保存完了時点で見積IDを画面に返す |
| **書き戻しを1回に** | 保存時の行番号を引き継ぎ、再検索せずまとめて更新。連続する列は1回の `setValues` |
| **ログをバッファリング** | リクエスト終了時に1回だけ書き込み |
| **明細書き込みをバッチ化** | 64回 → 列ごと4回の `setValues` |
| **採番を1列読みに** | `estimate_id` 列だけ読む |
| **PDF専用テンプレート（任意）** | `adminCreatePdfTemplate()` で差し込み2シートだけの軽いファイルを作成。見積データが増えても複製時間が伸びない |
| **固定sleepを削除** | `SpreadsheetApp.flush()` のみ |

### 体感の見込み

| 操作 | 旧 | 新 |
|---|---|---|
| 初期表示（初回） | 20〜35秒 | 3〜5秒 |
| 初期表示（2回目以降・6時間以内） | 20〜35秒 | 1秒未満 |
| 入力中の金額再計算 | 1操作ごとに2〜5秒 | **0秒（通信なし）** |
| 見積作成 → 見積ID表示 | 50〜80秒 | 2〜4秒 |
| 見積作成 → PDF・下書き完了 | 50〜80秒 | 10〜18秒 |

数値は構成から見積もったもの。デプロイ後に `adminBenchmark()` でマスタ読み込みの実測値が取れる。

## 2. 変則割引

3つの入れ方を用意した（オーナー選択どおり。割引プリセットのマスタ化は今回見送り）。

### ① 見積全体への調整行（基本）

「5. 割引・調整」で追加する。1件の見積に何行でも入れられる。

| 項目 | 内容 |
|---|---|
| 名称 | 自由入力。**入力した名称がそのまま見積書PDFに印字される**（例：初回サービス割引） |
| 値引き / 割増 | どちらも可。追加作業費などは割増で入れる |
| 円 / % | 定額と率を選べる |
| 率の対象 | 課税対象計（繁忙期加算を含む）／ 明細小計 |
| 税区分 | 課税＝消費税も連動して下がる／非課税＝税込での値引き（消費税額は変わらない） |

### ② 明細ごとの値引き

各メニュー行の「値引き」ボタンで、その行だけの値引き（円 or %）を入力する。
「この1台だけ古いので2,000円引き」のような現場対応向け。

PDFでは**独立した行**として出るので、`単価 × 数量 = 金額` が崩れない。

```
エアコンクリーニング（ノーマル）      2   9,800   19,600
エアコンクリーニング（ノーマル） 値引き 1  -2,000   -2,000
```

### ③ 合計を指定額に合わせる

「税込合計をこの金額にする」に金額を入れると、差額を `端数調整` として自動で足し引きし、
**指定額ちょうど**に着地する。切り上げ方向（割増）も可。

端数調整は非課税（税込）の調整として入れている。課税側で調整すると消費税の丸めで数円ずれ、
1円合わせるのに2行必要になるため。書類上は `小計 + 消費税 = 合計` が常に成立する。

### ガードレール

- 明細金額を超える値引きは自動で切り詰める
- 課税値引きは課税対象を超えて引かない（消費税がマイナスにならない）
- 手動値引き・割増を入れると**確認事項に必ず表示**される
- 明細小計の30%以上の手動値引きは追加で警告（閾値は設定マスタ `large_discount_alert_ratio`）
- PDF明細が16行を超える場合、調整行を「各種割引・調整」1行に自動集約して警告を出す
- **ロックはしない。** 例外があってもPDF・メール下書きは作成できる（引継ぎ仕様どおり）

### 代表者確認の扱い

オーナー指定により、**手動値引きはアラート表示のみ**。代表者確認メールは求めない。
確認事項を2段階に分けた。

| 区分 | 内容 | 代表者確認ボタン |
|---|---|---|
| 代表者確認の対象 | 単価未設定、要確認事項、法人/事業者、空室清掃、50台超、高速代、備考「要確認」、繁忙期/自動割引の手動変更、16行超 | **出る** |
| 内容確認 | 手動値引き・割増、明細値引き、端数調整、大幅値引き警告 | 出ない |

見積データには `例外フラグ`（従来どおり）に加えて `要代表者確認` 列を追加して両方記録する。

## 3. 構成

```
apps/estimate-app/
├── src/                          ← GASプロジェクトへ貼るファイル
│   ├── code.gs                   サーバー：API・マスタ読み込み・PDF・Gmail・シートIO
│   ├── Admin.gs                  管理者専用：セットアップ／正規化／診断／バックアップ
│   ├── Calc.html                 計算エンジン（クライアントとサーバーで共有）
│   ├── Index.html                画面
│   ├── style.html                CSS
│   └── JavaScript.html           クライアント
├── master/                       マスタ貼り付け用TSV（toolsから自動生成）
├── tools/                        Nodeで動く検証スクリプト
└── docs/
    ├── README.md                 この文書
    ├── acceptance-test.md        受入テスト
    └── legacy-*.txt              引継ぎ資料に入っていた旧コード（差分確認・切り戻し参照用）
```

> `legacy-*.txt` は引継ぎZIPの `current_code` のコピーであり、**本番そのものではない**。
> 差し替え前に、必ず本番GASの実ソースと突き合わせること。

### 計算エンジンを1つに保つ仕掛け

`Calc.html` は `<script>` 1本で `CalcEngine` を定義している。

- クライアント：`Index.html` が `include('Calc')` で読み込む
- サーバー：`getCalcEngine_()` が同じファイルを読んで `eval` する

同じ関数を2箇所で実装しないので、**画面の合計とPDFの合計がずれない**。
`tools/record-roundtrip-test.js` がこの一致を毎回検証している。

### GASを続ける判断について

「GASに拘るつもりはない」とのことだったが、**GASのまま直すのが正解**と判断した。

- 遅さの原因はGASではなく、シートAPIの往復が1操作あたり100回以上あったこと。往復を減らせば解決する
- 料金マスタはオーナーが手で編集するスプレッドシートそのもの。DBに移すと二重管理になる
- `info.onehitter@gmail.com` としてのGmail下書き作成・Drive保存が標準機能で使える。外部化するとOAuth基盤とサーバー運用が要る
- ホスティング費用・運用ゼロ
- 業務用スマホが常時ログインしている前提の運用がそのまま維持できる

外に出して得られるのは主にUIの自由度だが、今回の2つの困りごとはどちらもUIの問題ではなかった。

## 4. デプロイ手順

Apps Scriptエディタ（`info.onehitter@gmail.com`）で作業する。

### 手順0：現行を保存する（必須）

1. 現行GASの4ファイル（`code.gs` / `Index.html` / `style.html` / `JavaScript.html`）の中身を
   ローカルにコピーして保存する
2. 現在のデプロイID・WebアプリURLを控える
3. エディタで `adminBackup()` を実行する前に、**先に手順1でファイルを差し替える必要がある**ため、
   バックアップは手動で行うか、手順1のあと最初に `adminBackup()` を実行する

> `current_code` は最後に納品されたコードのスナップショットであり、本番そのものではない。
> 差し替え前に本番の実ソースを必ず控えること。

### 手順1：ファイルを差し替える

| GASのファイル名 | 置くもの |
|---|---|
| `code.gs` | `src/code.gs`（全文置換） |
| `Index.html` | `src/Index.html`（全文置換） |
| `style.html` | `src/style.html`（全文置換） |
| `JavaScript.html` | `src/JavaScript.html`（全文置換） |
| `Admin.gs` | **新規作成**（スクリプト）して `src/Admin.gs` を貼る |
| `Calc.html` | **新規作成**（HTML）して `src/Calc.html` を貼る |

> `Calc.html` を作り忘れると `getCalcEngine_()` が失敗する。必ず作ること。
> ファイル名は大文字小文字まで一致させること。

### 手順2：管理者関数を順に実行する

エディタ上部の関数プルダウンから選んで実行する。

| 順 | 関数 | 内容 | 必須 |
|---|---|---|---|
| 1 | `adminBackup()` | マスタと帳票/DBを複製して退避 | ○ |
| 2 | `adminDiagnose()` | 現状確認（読むだけ） | ○ |
| 3 | `adminSetup()` | 不足シート・不足列・不足設定キーを補う | ○ |
| 4 | `adminNormalizeDiscountRules()` | 割引繁忙期マスタを正規化（155行 → 16行） | ○ |
| 5 | `adminNormalizeMailTemplates()` | メールテンプレートマスタを正規化（161行 → 5行） | ○ |
| 6 | `adminNormalizeCellDefinitions()` | 差し込みセル定義の列ずれを修復 | ○ |
| 7 | `adminDiagnose()` | もう一度実行して警告が消えたか確認 | ○ |
| 8 | `adminCreatePdfTemplate()` | PDF生成専用テンプレートを作成 | 任意 |
| 9 | `adminSetMasterTimezone()` | マスタのTZを Asia/Tokyo に統一 | 任意 |
| 10 | `adminRefreshCache()` | マスタキャッシュを破棄 | ○ |

`adminSetup()` は既存の列位置を動かさない。追加列は右端に足すだけ。

手順4〜6は元シートを `<シート名>_旧_YYYYMMDD_HHmm` にリネームして退避してから
新しいシートを作る。**元データは消えない。**

手順8を実行した場合は、表示されたIDを設定マスタの `pdf_template_spreadsheet_id` に貼り、
もう一度 `adminRefreshCache()` を実行する。

### 手順3：デプロイ

「デプロイを管理」→ 既存デプロイを編集 → バージョンを「新バージョン」にして更新。
**新規デプロイを作らないこと**（URLが変わり、現場のブックマークが切れる）。

- 実行するユーザー：自分（スクリプト所有者）
- アクセスできるユーザー：現行のまま

### 手順4：受入テスト

`docs/acceptance-test.md` を上から実施する。

## 5. マスタ変更内容

`adminNormalize*()` を実行すれば自動で反映される。
手で貼りたい場合のためにTSVも用意した（`master/`）。

| ファイル | 貼り付け先 |
|---|---|
| `割引繁忙期マスタ_正規化.tsv` | 割引繁忙期マスタ（A1から。既存行は削除してから） |
| `差し込みセル定義_正規化.tsv` | 差し込みセル定義（A1から。既存行は削除してから） |
| `設定マスタ_追加分.tsv` | 設定マスタの**末尾に追記**（ヘッダー行は貼らない） |

メールテンプレートは本文に改行が含まれTSVで壊れるため、`adminNormalizeMailTemplates()` を使うこと。

### 追加される設定キー

| 設定キー | 初期値 | 意味 |
|---|---|---|
| `auto_discount_enabled` | `FALSE` | 早期予約割引・複数台割引の自動判定を使うか。**現場周知後に `TRUE` へ** |
| `large_discount_alert_ratio` | `0.30` | 手動値引きがこの割合以上で警告 |
| `pdf_template_spreadsheet_id` | 空 | PDF生成専用テンプレートのID |

### 見積データに追加される列（右端に追加。既存列は動かない）

`要代表者確認` / `自動割引種別` / `自動割引額` / `明細値引き合計` / `調整合計額` /
`合計指定額` / `調整_JSON` / `調整01〜05_名称` / `調整01〜05_金額` / `明細01〜16_値引き額`

`調整_JSON` は複製編集で調整行を正確に復元するための正本。
`調整NN_名称` `調整NN_金額` はシートを人が読むための表示用。

## 6. 検証

Nodeで実行できる。GASにデプロイせずに計算ロジックを確認できる。

```bash
node apps/estimate-app/tools/calc-test.js             # 計算エンジン 46ケース
node apps/estimate-app/tools/record-roundtrip-test.js # 保存→復元の一致 56ケース
node apps/estimate-app/tools/gen-master-tsv.js        # マスタTSVを再生成
```

`record-roundtrip-test.js` は `code.gs` を実際に評価して
`calculateEstimate_` → `buildEstimateRecord_` → `rebuildCalcFromRecord_` を通す。
画面の合計とPDFの合計が一致することを保証している。

`calc-test.js` は受入テスト C（繁忙期）・D（割引）を固定ケース化したもの。
引継ぎ資料のP0-8「自動繁忙期・割引判定をユニットテスト相当で検証する」に対応する。

| **宛先メール未設定の提出先** | クラスリフォーム／遼／才木工業。PDFは作れるがGmail下書きが作れない。画面にも警告を出すようにした |
| **メニューマスタの重複列** | 後半の旧列（単価／標準時間／単位／繁忙期対象／請求書流用対象／備考）は全行空。動作に影響しないので今回は残した。安定後に削除推奨 |
| 二重クリック対策 | クライアント側のボタン無効化のみ。リクエストIDによる冪等化は未実装 |
| 現場社員の識別 | 「担当者」入力に依存。担当者マスタ＋プルダウン化は未実装 |
| マスタ変更の反映 | キャッシュは6時間。マスタを編集したら `adminRefreshCache()` を実行するか6時間待つ |

## 9. 変更していないこと（引継ぎ仕様の遵守）

- Gmailは `createDraft()` のみ。即送信するコードは存在しない
- 高速料金の自動取得なし。手入力とリンクのみ
- 見積画面に駐車場代の入力欄なし。備考に定型注記のみ
- 過去見積の直接編集なし。複製時は新しい見積IDを発行し `複製元見積ID` を保持
- 例外時もPDF・メール下書き作成をロックしない
- 明細は最大16行。超過は例外表示
- PDFはテンプレートの一時コピー方式。一時ファイルは必ずゴミ箱へ
- 列番号の固定参照なし。すべてヘッダー名で解決
- スマホ最優先のUI
