# 法人向け作業報告書：設計の骨組み（草案 v0・2026-11-07）

オーナー決定（11/5 第9回MTG）：**報告書は法人のみ**。個人のお客様向けは作らない。
過去に和真さんが法人へ送った報告書（メール・ドライブ）から**型を割り出し**、作業完了フォーム（＋写真）から**下書きを自動で作る**。
期限：設計1枚 11/12、試作1件 11/16 MTG。**この草案は、資料が届く前の骨組み**。★の箇所は、資料を見て確定する。

## 1. 報告書に載せる項目と並び（案）
| # | 項目 | 元になるデータ | 和真さんの入力 |
|---|---|---|---|
| 1 | 宛名（元請の法人名・御中） | 提出先マスタ（案件タイプ） | なし |
| 2 | 件名「作業報告書」＋案件名／物件名 | 見積・請求の案件名 | なし |
| 3 | お客様名・現場住所 | 見積・請求の顧客名・現場住所 | なし |
| 4 | 作業日（＋作業時間 ★要否） | 見積・請求の施工日／完了フォーム | なし（時間は任意） |
| 5 | 担当者 | 見積・請求の担当者 | なし |
| 6 | 作業内容（メニュー・数量） | 見積・請求の明細 | なし |
| 7 | 作業前の状態（所見） | 完了フォームの3択＋自由記述（任意） | 0〜1タップ |
| 8 | 作業後の状況・試運転（エアコン等） | メニュー別の決まり文（自動） | なし（やっていないときだけ外す） |
| 9 | 写真（作業前・作業後） | 写真フォルダ（Drive）★ | 写真を送る（下の注） |
| 10 | 特記事項（不具合・追加作業・申し送り） | 完了フォーム（任意） | 任意 |
| 11 | 次回の目安（★法人は要るか） | メニューマスタ「次回の目安」＋施工日 | なし |
| 12 | 紐付け（見積番号／請求番号） | 見積・請求の番号 | なし |
**★ 法人ごとに必要な項目・様式が違う可能性が高い**（過去の報告書で確認）。型は「共通の骨組み＋法人別の差分（出す項目・文言・写真の枚数）」で持つ。

## 2. 自動で作る流れ
1. 作業完了フォーム（cmo 側・すでに稼働）が、見積番号（または請求番号）と、7・10・写真フォルダのリンクを、見積アプリの外部API（合言葉つき）に送る
2. 見積アプリが、**見積・請求のデータ**から1〜6・11・12を埋め、**法人別の型**で報告書PDFを作る
3. **Gmail の下書き**を作る（宛先は提出先マスタ。**即送信はしない**。宛先は台帳と機械照合してから下書きを作る。照合できなければ止める）
4. 和真さんは下書きを確認して送る（今と同じ）
- 新しい入力欄は「作業前の状態」「特記事項」だけ。写真はフォルダに入れるだけ。
- 実装場所：コード.js（既存の5ファイル構成の中。新しいファイルは作らない）＋帳票スプレッドシートに「作業報告書」の雛形タブ（法人別は雛形の差分で持つ）。
- 守ること：請求書・見積書の様式、通常見積の金額は変えない／例外があってもPDF・下書きを止めない／明細16行まで／資格情報をコミットしない。

## 3. 「過去の報告書から学ぶ」のやり方（資料が届いたら）
1. 法人ごとに、過去の報告書を1〜3件ずつ読み、項目・文言・写真の並びを書き出す
2. 共通部分＝骨組み、法人ごとの違い＝差分表（出す項目・敬称・挨拶文・写真枚数・提出タイミング）にまとめる
3. 文言は**原文をそのまま使う**（言い回しを変えない）。メニュー別の決まり文（試運転・作業後の状況）も、過去の原文から拾う
4. 試作：最も件数の多い法人1社の1件で、**過去の報告書と並べて差を目視**

## 4. 資料が届くまでに決まっていないこと（★）
- 写真：どう集めるか（Drive フォルダ＋枚数チェックが第一案。10/29 の検討メモ参照）
- 法人ごとの必須項目・様式・送る日（資料で確認）
- 作業時間・次回の目安を法人向けに載せるか
- 誰に・いつ送るか（当日／翌日）と、台帳の宛先照合の置き場

## 5. スケジュール（案）
11/12 設計1枚（資料を反映した版）→ 11/16 試作1件（過去の報告書と並べて確認）。資料が11/10までに届かない場合は、骨組みのまま法人1社の「型」を暫定で作り、届き次第差し替える。
