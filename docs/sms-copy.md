## 2. 何を言うか（訴求の設計）

冬季の割引は **ありません**（早期予約割引は11〜12月＝0%）。
値引きが使えないので、代わりに**事実**を2つ使います。どちらも `data/prices.json` で裏が取れます。

### ① 12月から繁忙期料金 +3,300円 → 「11月中なら通常価格」

`data/prices.json` の `繁忙期加算.対象月` は 5・6・7・**12月**。
11月は加算なし、12月からは1箇所あたり+3,300円です。

**値引きではなく「値上げ前」を伝えるので、二重価格表示になりません。**
年末LP（`lp/nenmatsu/`）も同じ「11月30日までのご予約なら通常価格」で作られているので、話が揃います。

### ② 同時施工なら1箇所3,300円お得

浴室・キッチン・レンジフードは 単体18,480円 → 同時施工15,180円。差額がちょうど3,300円です。
**最大の商機であるクロスセル（エアコンのみ621名／潜在3,100万円）に、そのまま効きます。**

差し込みには台帳の「今回おすすめ」列をそのまま使います。内訳は
換気扇・浴室 85／浴室・キッチン 28／換気扇・キッチン 18／キッチン・洗濯機 9／換気扇・洗濯機 1。

### 使わなかったもの（理由つき）

| 使わなかった訴求 | 理由 |
|---|---|
| 「満足度98.6%」 | 根拠はあるが、SMSでは分母（209名中206名・2023年1月〜2025年12月）を併記する余白がない。**分母なしの数字は優良誤認になりうる。** LPと公式LINEで使う |
| 「残りわずか」「枠が埋まります」 | **事実に反する。** 稼働率はピークでも65%、9〜12月は約940時間空いている。根拠のない緊急性は景表法上あぶない |
| 「通常◯◯円→今なら◯◯円」 | 価格改定が2026-09-06。旧価格を「通常価格」として並べる二重価格表示は、最近相当期間の販売実績という要件を満たさない |
| 「業界最安」「地域No.1」 | 裏付けがない |

## 4. 法令の自己点検

### 特定電子メール法（SMSも対象です）

**電話番号を宛先とするSMSは「特定電子メール」に含まれます。** メールと同じ規制がかかります。

| 論点 | 判定 | 根拠 |
|---|---|---|
| オプトイン（事前同意） | **不要** | 送信先は全員、施工の際にご自身で電話番号を通知くださった既存のお客様。法3条1項の「自己の電子メールアドレスを通知した者」「取引関係にある者」に当たる |
| 送信者の表示（法4条） | **対応済み** | A案は `【ワンヒッター】`、B案は `ワンヒッターの渡辺です。` で始まる。`tools/sms_build.py --check` が冒頭30文字に社名があるかを機械的に検算する |
| 受信拒否の通知先（法4条） | **対応済み** | 全テンプレートの末尾に「不要な方は『停止』と返信」を入れている |
| 記録の保存 | **要対応** | 「停止」と返信された番号を止める運用が要る（§5） |

> ⚠️ **1つだけ未確認があります。** 送信元番号への返信をこちらで受け取れるかは、
> KDDIの契約形態（共通番号か自社番号か）次第です。**返信を受け取れない契約だった場合、
> 「停止」返信は誰にも届きません。** その場合は文面を
> 「配信停止は080-8043-8259へ」に差し替えます。**申込時にKDDIへ確認する項目に入れました。**

### 景品表示法

| 論点 | 判定 |
|---|---|
| 有利誤認（二重価格） | **回避済み。** 旧価格との比較を一切していない。「+3,300円が12月から」は将来の値上げ予告であって、架空の割引ではない |
| 有利誤認（同時施工3,300円） | **OK。** 単体18,480円と同時施工15,180円の実際の差額。`data/prices.json` が根拠 |
| 優良誤認（満足度） | **回避済み。** SMSには数字を入れていない |
| 緊急性の演出 | **回避済み。** 「残りわずか」等は使っていない |

`tools/sms_build.py --check` が、文面に書いた金額を `data/prices.json` と突き合わせて検算します。
**文面をいじったら必ず通してください。**

### 個人情報

- 宛先リストは `private/` に置き、`.gitignore` で除外しています。**リポジトリに入りません。**
- 送信結果のログでも電話番号はマスクして表示します。
- API認証情報は環境変数からしか読みません（`tools/sms_send.py`）。

## 5. 送信の手順（承認が出たあと）

```bash
# 1. 「冬季見込み客_2026」タブをCSVで private/ に置く
# 2. 組み立てて中身を確認する（まだ送らない）
python3 tools/sms_build.py --csv private/冬季見込み客.csv --variant b --sample

# 3. 送信キューを書き出す（--variant a なら会社名で名乗る案）
python3 tools/sms_build.py --csv private/冬季見込み客.csv --variant b --out private/queue.jsonl

# 4. 送らずに最終確認
python3 tools/sms_send.py --queue private/queue.jsonl --dry-run

# 5. まず1件だけテスト送信（オーナーの携帯宛て）
python3 tools/sms_send.py --queue private/queue.jsonl --limit 1 --confirm SEND

# 6. 本送信（★ここでオーナーの承認を取る）
python3 tools/sms_send.py --queue private/queue.jsonl --confirm SEND

# 7. 結果の集計
python3 tools/sms_send.py --result private/result-*.jsonl --report
```

`tools/sms_send.py` は **`--confirm SEND` が無いと絶対に送りません。**
また `private/sms-provider.json`（APIの仕様を書き写す設定ファイル）が無い状態でも送りません。
**KDDIのAPI仕様は非公開なので、推測で書かず、届いた仕様書のとおりに書き写してください。**

| 便 | 時期 | 内容 |

### 送信後にやること

1. 結果ログの失敗分を、台帳の電話番号の状態を「要確認」に落とす（次回から除外される）
2. 「停止」と返信された番号を**配信停止リストに載せ、以後すべての便から外す**
3. 入電・LINE友だち追加・受注をセグメント別に記録する（§6）

## 6. 効果測定

SMSはクリック計測ができません（短縮URLを挟まない限り）。なので**入口ごとに分けて数えます。**

| 指標 | 数え方 | 置いた目標 |
|---|---|---|
| 到達率 | 送信APIの成功数 ÷ 送信数 | 90%。下回るなら名簿の鮮度に問題がある |
| LINE友だち増 | 配信前後の友だち数の差 | 送信61名に対し**6名**（10%） |
| 入電 | 受付で「SMSを見て」と言われた件数 | 送信61名に対し**3件**（5%） |
| 受注 | 上記からの成約 | **2件**。優先1・2の平均単価から見て売上10万円前後 |
| 費用対効果 | 受注額 ÷ 送信費用 | 送信費用は約1,700円。**1件でも取れれば回収できる** |

> 目標値は実測が無いための仮置きです。**第1便の実績が出たら置き直します。**
> 数える仕組みが無いと何も分からないので、受付での一言（「どちらでお知りになりましたか」）だけは
> 必ず記録してください。
