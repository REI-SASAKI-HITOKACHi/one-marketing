作成 2026-09-06 ／ 計測担当スレッド

必ずこのファイルと `tracking/events.js` の両方を直してください。

関連：`docs/measurement-audit.md`（現状）／`docs/measurement-owner-steps.md`（オーナー作業）／
`docs/calltracking-vendors.md`（電話計測の事業者比較）

## 1. 何を測るのか（設計の前提）

事業側の成果地点は **「作業完了ベース／成果単価3,000円」** です。
これはウェブ上では観測できません。**作業が終わったかどうかはウェブに現れない**ためです。

そこで、ウェブ側は**「申込が発生した」までを測り、そこから先は台帳で突き合わせる**、
という二段構えにします。

```
広告費 ──→ 表示 ──→ クリック ──→ LP閲覧 ──→ 申込      ──→ 現地見積 ──→ 作業完了
                                            ↑ここまでがGA4    ↑ここから先は台帳（スプレッドシート）
```

したがって GA4 の数字だけを見ても、CPA（成果単価）は出ません。
**GA4の「申込数」と、台帳の「成約数」を月次で突き合わせる運用が要ります**（第8章）。

申込の入口は2つあります。**両方を測らないと、成果の半分が抜けます。**

| 入口 | 測り方 | 難易度 |
|---|---|---|
| WEBフォーム | 送信完了ページで数える | 実装済み |
| **電話** | コールトラッキング。**まずGoogle広告の無料機能で** | 未導入 |

## 2. ページの識別（すべてのイベントに付く）

A/Bテストを後から比べられるように、**全イベントに次の3つを付けています。**

| パラメータ | 値 | 意味 |
|---|---|---|
| `lp_id` | `aircon` / `mizumawari` | どの商品のLPか |
| `lp_variant` | `A` / `B` | A/Bテストのどちらのパターンか |
| `page_kind` | `lp` / `thanks` / `survey` | LP本体か、送信完了ページか、アンケートか |

**案A（`/aircon/`）と案B（`/aircon-b/`）は、`lp_id` を同じ `aircon` に揃えてあります。**
違うのは `lp_variant` だけです。こうしておくと、GA4のレポートで
「エアコンLP全体」を1行で見たあと、`lp_variant` で内訳に割ればA/Bが並びます。
`lp_id` を別々にしてしまうと、この2段階の見方ができません。

| ページ | `lp_id` | `lp_variant` | `page_kind` |
|---|---|---|---|
| `/aircon/` | `aircon` | `A` | `lp` |
| `/aircon/thanks.html` | `aircon` | `A` | `thanks` |
| `/aircon-b/` | `aircon` | **`B`** | `lp` |
| `/aircon-b/thanks.html` | `aircon` | **`B`** | `thanks` |
| `/mizumawari/` | `mizumawari` | `A` | `lp` |
| `/mizumawari/thanks.html` | `mizumawari` | `A` | `thanks` |
| アンケート（別サイト） | `survey` | `A` | `survey` |

この対応表は `tools/build-site.py` の `PAGES` が持っています。
新しいLPを足すときは、そこに `lp_id` と `lp_variant` を書けば自動で付きます。

## 3. イベント一覧

GA4の自動収集イベント（`page_view`、`session_start`、`first_visit`、`user_engagement` など）は
設定不要で入るので、ここには書きません。**以下は自前で送っているものだけです。**

### 3-1. 成果として数えるもの

| イベント名 | いつ送るか | 追加パラメータ |
|---|---|---|
| **`generate_lead`** | **送信完了ページが表示されたとき** | `value`（円）／`currency`＝`JPY`／`estimate_total` |
| **`phone_click`** | 電話番号（`tel:` リンク）が押されたとき | `link_position`／`phone_number` |
| **`line_click`** | LINEのボタンが押されたとき | `link_position` |

**`generate_lead` を「送信ボタンを押したとき」ではなく「完了ページが出たとき」にしている理由：**
送信ボタンは、入力エラーでも、通信が切れても、二度押ししても発火します。
**完了ページは、Netlify Forms が申込を受理したあとにしか表示されません。**
成果を水増ししないために、こちらを正としています。

**`phone_click` は「電話が繋がった」ではありません。** 押しただけで、
かけずにやめた人も、話し中も、全部含みます。**実際の着信数は別で測る必要があります**
（第6章）。それでも、無いよりは桁違いにマシなので、暫定の成果として置いています。

### 3-2. 途中経過（どこで落ちているかを見るため）

| イベント名 | いつ送るか | 追加パラメータ |
|---|---|---|
| `cta_click` | ページ内リンク（`#form` など）が押されたとき | `link_position`／`link_target` |
| `estimate_use` | 料金シミュレーターを触ったとき（**1ページ1回だけ**） | — |
| `area_check` | 「エリアを確認」ボタンを押したとき | `area_result` |
| `form_start` | 予約フォームに最初にカーソルが入ったとき（**1回だけ**） | — |
| `form_submit` | 送信ボタンを押したとき | `estimate_total` |
| `scroll_depth` | 25 / 50 / 75 / 90% まで読まれたとき | `percent_scrolled` |

`estimate_use` と `form_start` を1回だけにしているのは、
**触るたびに送ると人数ではなく操作回数になってしまい、離脱率が読めなくなる**ためです。

### 3-3. アンケート（`one-hitter-survey.netlify.app`）だけのもの

アンケートは**4画面のウィザードで、途中でページが変わりません。**
そのため「開いた人のうち何人が最後まで答えたか」も「どの画面で脱落したか」も、
いまはまったく分かりません。次を送って、そこを埋めます。

| イベント名 | いつ送るか | 追加パラメータ |
|---|---|---|
| `survey_start` | 最初の設問に触れたとき（**1回だけ**） | — |
| `survey_step` | その画面が表示されたとき（**1画面につき1回**） | `step_number`（1〜4） |
| **`survey_complete`** | **回答が送信され、完了画面が出たとき** | — |
| `review_copy` | 「クチコミの下書きをコピー」を押したとき | — |
| `google_review_click` | Googleのクチコミ投稿画面へのリンクを押したとき | — |
| `refer_copy` | 紹介文をコピーしたとき | — |
| `refer_share` | 紹介文をLINEで送るリンクを押したとき | `share_to`＝`line` |
| `private_send` | 非公開のご意見を送ったとき | — |

**回答率 ＝ `survey_complete` ÷ `page_view`。** これがQRの運用が効いているかの指標です。
`survey_step` を並べれば、4画面のどこで人が抜けているかが分かります。

`survey_complete` は**送信が終わってからしか出ない完了画面**を見て送っているので、
「途中でやめた人」を数えることはありません。

> **LPの `line_click` とは別名（`refer_share`）にしています。**
> LPのLINEは「公式アカウントの友だち追加」で成果（キーイベント）ですが、
> アンケートのLINEは「友だちに紹介文を送る」で意味が違います。
> 同じ名前にすると、成果の件数が混ざります。

> `survey_complete` を**キーイベントにするかは、目的しだいです。**
> 広告の成果ではないので、**指定しないことを勧めます**（広告の入札が歪みます）。
> レポートで件数を見るだけなら、指定は要りません。

### 3-4. パラメータの値

| パラメータ | 取りうる値 |
|---|---|
| `link_position` | `header` / `hero` / `estimate` / `form` / `sticky` / `footer` / `thanks` / `other` |
| `area_result` | `in_area`（対応エリア）／`out_of_area`（エリア外）／`invalid`（入力不備） |
| `percent_scrolled` | `25` / `50` / `75` / `90` |
| `estimate_total` | 料金シミュレーターの合計額（円・税込）。触っていなければ `0` |
| `phone_number` | `tel:` リンクの番号（数字のみ）。コールトラッキングの番号が入っていれば、その番号 |

`link_position` は、押されたリンクの祖先をたどって決めています
（`.sticky` → `sticky`、`.bar` → `header`、`#form` → `form` …）。
**同じ「電話」でも、ヘッダーで押されたのか、読み終わって追従バーで押されたのかは
意味がまったく違う**ので、分けています。

### 3-5. `area_result` は捨てないでください

`out_of_area` の件数は、**エリア拡大の判断材料そのもの**です。
「対応していない地域から、どれだけ人が来ているか」が分かるのは、ここだけです。

## 4. 見積り金額の引き継ぎ

料金シミュレーターの合計額を、**送信完了ページの `generate_lead` まで持ち越しています。**

```
LP                                        送信完了ページ
─────────────────────────                 ─────────────────────
シミュレーターで 28,160円 を選ぶ
      ↓
送信ボタン → form_submit
             estimate_total: 28160
      ↓
      sessionStorage に保存  ─────────→  読み出して消す
                                              ↓
                                        generate_lead
                                        value: 28160, currency: JPY
```

**なぜ必要か：** 金額が入っていると、Google広告が「高い申込を取れるキーワード」に
自動で寄せてくれます（入札の最適化）。全部の申込を同じ1件として扱うより、
広告費の使われ方が良くなります。

**金額の決まり方（上から順に採用）**

1. お客様がシミュレーターで選んだ合計額
2. `tracking/measurement.json` の `lead_value`（LPごとの想定単価）
3. どちらも無ければ、**金額は送りません**（0円として送ることはしません）

> ⚠️ **これは「見積り額」であって、受注額でも粗利でもありません。**
> 実際にいくらになるかは現地見積りで決まります。**GA4の「収益」欄に出てくる数字を
> 売上として読まないでください。** 広告の入札を賢くするための目安です。

sessionStorage が使えない環境（プライベートブラウズ等）でも、**成果自体は必ず記録されます。**
金額が付かないだけです。

## 5. コンバージョン（キーイベント）の設定

GA4では、成果として扱いたいイベントを「キーイベント」に指定します。
**指定しないと、Google広告に取り込めません。**

| イベント | キーイベントにするか | 位置づけ |
|---|---|---|
| `generate_lead` | **する** | 主要成果。これが伸びているかで判断する |
| `phone_click` | **する** | 暫定の成果。コールトラッキング導入後は置き換える |
| `line_click` | する | 副次成果。すぐ申込にならないが、あとで効く |
| `form_submit` | **しない** | `generate_lead` と二重に数えてしまう |
| その他 | しない | 途中経過を見るためのもの |

設定手順は `docs/measurement-owner-steps.md` の第2章。

### Google広告のコンバージョン

`tracking/measurement.json` の `google_ads.labels` に、**イベント名と同じキー**で
ラベルを入れると、そのイベントが発生したときGoogle広告にもコンバージョンが送られます。

```json
"google_ads": {
  "conversion_id": "AW-1234567890",
  "labels": {
    "generate_lead": "xxxxxxxxxxxxxxx",
    "phone_click":   "yyyyyyyyyyyyyyy",
    "line_click":    ""
  }
}
```

**キー名はイベント名と1文字も違えてはいけません**（`lead` ではなく `generate_lead`）。
違うと、エラーも出ずに、静かに送られません。

なお、**GA4のキーイベントをGoogle広告に読み込ませる方法もあります**（アカウントをリンクして
インポートするだけ）。管理する場所が1つで済むので、**基本はそちらを推奨**します。
上の `labels` は、GA4を経由せず直接送りたい場合の逃げ道です。

## 6. 電話をどう測るか（3段構え）

**電話は「押した」と「繋がった」が別物です。** 段階を分けて考えます。

| 段階 | 何が分かるか | 費用 | 状態 |
|---|---|---|---|
| ① `phone_click` | タップ数。LPごと・場所ごと | 0円 | **実装済み** |
| ② Google広告の転送番号 | **実際の着信数・通話時間・キーワード** | **0円** | 未導入 |
| ③ コールトラッキング契約 | 上に加え、Google広告以外の流入も | 月2,200円〜 | 未導入 |

### ②が要になります

Google広告には、**広告経由で来た訪問者にだけ、LP上の電話番号を専用の転送番号に
自動で差し替える機能**があり、**無料**です。かかってきた電話は、そのまま
080-8043-8259 に転送されるので、受電の仕方は今と変わりません。

さらに **「◯秒以上の通話だけを成果として数える」設定**ができます。
間違い電話や営業電話を弾けるので、**成果単価3,000円という基準に照らした判断がすぐできます。**

**限界：Google広告経由の電話しか測れません。** Yahoo!広告、Googleビジネスプロフィール、
チラシ、紹介からの電話は測れません。それでも、**広告費を判断するには十分です**
（広告費の是非を判断したいのだから、広告経由が測れれば足ります）。

### ③に進むときは

`tracking/measurement.json` の `call_tracking.numbers` にLPごとの番号を書いて再ビルドするだけで、
**表示も `tel:` リンクも差し替わります。** LPの本文は触りません。

```json
"call_tracking": {
  "default_number": "080-8043-8259",
  "numbers": { "aircon": "050-XXXX-XXXX", "aircon-b": "050-YYYY-YYYY", "mizumawari": "" }
}
```

空欄のLPは `default_number` のままです。`tools/check-tracking.py` が
**「aircon用の番号が mizumawari のページに紛れ込んでいないか」まで確認します。**
番号が混ざると計測の意味が消えるので、必ず配信前に通してください。

> ⚠️ **チラシ・名刺・Googleビジネスプロフィールの番号は、絶対に差し替えないでください。**
> LP専用の番号にLP以外からの電話が混ざると、何を測っているのか分からなくなります。

## 7. 実装がどこにあるか

| ファイル | 役割 | 触るとき |
|---|---|---|
| `tracking/measurement.json` | 測定ID・電話番号・想定単価 | **IDを入れるとき。ここだけ触れば足りる** |
| `tracking/events.js` | イベントを送る本体 | イベントを足す／変えるとき（この設計書も直す） |
| `tools/build-site.py` | 上の2つを全ページへ差し込む | 新しいLPを足すとき（`PAGES` に追記） |
| `tools/check-tracking.py` | 書き出したHTMLの確認 | **配信の直前に毎回** |
| `tools/templates/thanks.html` | 送信完了ページのひな形 | 完了ページの文言を変えるとき |
| `tools/inject-tracking.py` | **完結したHTML1枚に差し込む単体ツール** | アンケートや年末LPなど、LPの組み立てに乗らないページ |

### 手順

```bash
python3 tools/build-site.py netlify   # 書き出す
python3 tools/check-tracking.py       # 確認する（落ちたら直してから配信）
NETLIFY_TOKEN=... python3 tools/deploy-netlify.py   # 配信（※承認が要る）
```

**LPのソース（`lp/` 配下）には計測タグが入っていません。** 差し込みは書き出しのときだけです。
LPのデザイン・文言を別スレッドが変更しても、こちらと衝突しません。

### 動かないときの見方

`tracking/measurement.json` の `"debug"` を `true` にして再ビルドすると、
ブラウザの開発者ツールの「コンソール」に送信内容が `[OH計測]` として全部出ます。
**本番へ配信する前に、必ず `false` に戻してください。**

## 8. 数字をどう読むか（毎月やること）

GA4の数字だけでは、儲かったかどうかは判断できません。**台帳と突き合わせて初めて出ます。**

| 見る数字 | どこで | 何のため |
|---|---|---|
| LPの閲覧数 | GA4 | 広告が人を連れて来ているか |
| `generate_lead` の件数 | GA4 | 申込が発生しているか |
| `phone_click` の件数 | GA4 | 電話の入口がどれだけ押されたか |
| 実際の着信数 | Google広告の通話レポート | 押しただけでなく、繋がったか |
| **成約数・受注額** | **スプレッドシートの台帳** | **本当に売上になったか** |
| 広告費 | Google広告 | 使った額 |

**出したい数字**

```
CVR       ＝ generate_lead ÷ LP閲覧数            … LPが機能しているか
CPA（申込）＝ 広告費 ÷（generate_lead ＋ 着信数）  … 申込1件がいくらか
CPA（成約）＝ 広告費 ÷ 成約数                     … ← これが本番
ROAS      ＝ 受注額 ÷ 広告費                     … 使った額が返ってきたか
```

**A/Bテストの判定**は、GA4で `lp_variant` を内訳にして
「セッション数」と「`generate_lead` 数」を並べ、CVRを比べます。
判定の基準（何件たまったら決めるか）は `docs/ab-test-plan.md` 側の担当です。

> ⚠️ **申込1〜2件の差で勝ち負けを決めないでください。** その差はほぼ偶然です。

## 9. まだ埋まっていない穴（正直に書いておきます）

| # | 穴 | 影響 | どうするか |
|---|---|---|---|
| 1 | 実際の着信数が測れない | 成果の半分が見えない | Google広告の転送番号（0円）→ 手順書 第4章 |
| 2 | 公式サイトのフォーム送信が測れない | サイト経由の落ち込みの原因が切り分けられない | 完了画面の検知方法を制作会社に確認 |
| 3 | 申込 → 作業完了 の紐づけが手作業 | 成果単価3,000円の実績が自動で出ない | 台帳に「流入元」列を足す（第8章） |
| 4 | LINEの友だち追加が測れる範囲は限定的 | `line_click` はクリックまで | LINE公式アカウント側の分析と突き合わせ（別スレッド担当） |
| 5 | アンケートサイトに計測が入っていない | 回答率が分からない | 同じ仕組みを流用可能。ただしCMOスレッドの担当範囲 |
| 6 | Netlify Forms の受理数とGA4の件数が合わない可能性 | 迷惑投稿・二重送信の混入 | 月次でNetlifyの受信一覧と突き合わせる |

**1が最優先です。** 0円で、この業種で一番大きい入口が測れるようになります。
