# ワンヒッターのスレッド組織

**オーナーを経由せずに、スレッド同士が直接やり取りするための決まり。**

これまでは「LPスレッドの判断待ち」をオーナーが読んで、こちらに口頭で持ってきていた。
オーナーが交換機になっていて、そこで止まる。それをやめる。

---

## 1. 組織図

```
オーナー（佐々木 嶺）
  └ CMO ← ここが窓口。オーナーに上げるかどうかを決める
      ├ LP・サイト担当
      ├ 顧客接点担当（SMS・公式LINE）
      ├ 計測担当（GA4・広告タグ・電話CV）
      ├ 見積アプリ担当
      └ ネット流入施策担当（SNS＋メディア）
```

**オーナーに上げてよいのは、次の3つに当たるものだけ。**

1. お金を使う（広告出稿、有料サービスの契約、外注）
2. 外に出す（LP・サイトの公開、SNS投稿、顧客への一斉送信、PR作成）
3. 元に戻せない（データ削除、過去実績の書き換え、ドメイン設定の変更）

**それ以外は CMO が決める。** 各担当は CMO に聞き、CMO が答える。
「オーナーに確認します」で止めない。CMO が判断できないものだけ、CMO がまとめて上げる。

各役割の職務範囲・持ち物・禁止事項は `docs/org/roles/` にある。

**スレッドのタイトルは `役割名｜持ち物` で統一する**（接頭辞は付けない。オーナー指示）。
一覧で見たときに、どれが誰の仕事か分かるように。新しいスレッドを作るときも同じ形にすること。

---

## 2. 掲示板（`claude/org` ブランチ）

スレッド同士のやり取りは **`claude/org` という共有ブランチ**に置く。
自分の作業ブランチとは別なので、お互いの作業を壊さない。

読み書きは `tools/org.py` を使う。gitの操作は中でやる。

```
python3 tools/org.py 名簿                     # 誰がいるか
python3 tools/org.py 読む <自分の役割ID>       # 自分あての未処理
python3 tools/org.py 依頼 --from A --to B --件名 "..."   # 本文は標準入力
python3 tools/org.py 返信 <依頼ID> --from B             # 本文は標準入力
python3 tools/org.py 完了 <依頼ID>
python3 tools/org.py 現況 --from A            # 自分の現況を更新（標準入力）
python3 tools/org.py 一覧                     # 全部の依頼
```

**作業を始めるとき、いちばん最初に `読む` を実行すること。**
自分あての未処理が無ければ何も出ない。

## 3. 依頼の書き方

**受け取った側が、聞き返さずに動けるところまで書く。**
聞き返しが1往復増えるたびに半日が消える。

- 何をしてほしいのか（結論から）
- なぜ必要か（背景。これが無いと相手は判断を誤る）
- いつまでか
- 判断が要るなら、選択肢と、自分の推奨

**相手の持ち物を勝手に触らない。** 依頼を出して、相手にやってもらう。
どのディレクトリが誰の持ち物かは `docs/org/roles/` に書いてある。
LP配信のように事故が起きた場所は `docs/LP配信のルール.md` も読む。

---

## 4. 現況（`docs/org/status/<役割ID>.md`）

**区切りごとに自分の現況を更新する。** CMOはこれを読んで全体を見る。

- いま何をしているか
- 詰まっていること（誰の何を待っているか）
- 判断待ち（CMOに決めてほしいこと）

## 4.5 全スレッド共通の規則：お客様に届くものは「名乗り」を機械で照合する

2026-09-11、本舗名義のお客様3名にワンヒッター名義のSMSが届いた。送信系統の列を信じてリストを作っていたのが原因。
オーナー指示「絶対に再発させない。他のエージェントにも遵守させる仕組みに」。

- **決まり**：お客様に届くもの（SMS・LINE・メール・電話台本・DM）は、相手の名乗り（ワンヒッター／おそうじ本舗）を
  **台帳の「最新の施工の名義」と1人ずつ機械で突き合わせてから**作る。列の値・過去のリスト・記憶を信じない。
- **道具**：`tools/derive-soushin-keitou.py` の `meigi_hyou()`（電話番号／氏名 → 名義・最新施工日）。
  控えは `~/.cache/one-hitter/meigi-cache.json`（gitの外。電話番号が入るのでコミット禁止）。
- **食い違う相手・照合できない相手には送らない。** 「保留」にして、理由を残す。
- **本舗名義のお客様には**：ワンヒッターの名前・URL・受付番号・料金を出さない。導線は本舗の番号（080-1344-3137）と返信だけ。
- 新しい送信の道具を作るときは、この照合を**通さないと出力できない**作りにする（`tools/build-sms-list.py` が手本）。
- 該当する役割：cmo・crm（送信物を作る）。web-inflow（SNS・メディア）はお客様個人に送るものを作らないが、DMや返信を設計するときは同じ。

## 4.6 オーナーが直接そのスレッドに回答したとき（2026-09-11 オーナー指示）

- **オーナーの直接回答は、CMOの判断より優先する。** CMOの指示と食い違ったら、オーナーの回答に従い、CMOに知らせる。
- 受けたスレッドは**同日中に**、掲示板で `cmo` あてに **件名 `【オーナー決定】<要点>`** の依頼を出す。本文に**オーナーの発言を原文のまま引用**し、自分がどう動くかを1行添える。
- CMOはそれを `docs/cmo-savedata.md` の「オーナーの直接決定（原文）」に転記し、矛盾する自分の判断を取り下げる。CMOがいつでも読み返せる状態にしておくのが目的。
- オーナーへの質問は原則CMO経由（AskUserQuestion でオーナーに直接聞かない）。**ただしオーナーが自分からそのスレッドに来て話しているときは、その場で答えてよい。**

## 4.7 アフィリエイト（レントラックス）の担当は計測担当（2026-09-11 オーナー指示）

先方（株式会社レントラックス）とのやり取りが中心の仕事。文脈は `docs/アフィリエイト-レントラックス.md` に集約する（申込内容・受付番号・先方担当・落とし穴5点・提出物）。
計測担当が持つ：先方への連絡文の作成、提出物（出稿条件・ヒアリングシート）の下書き、成果地点「決済完了」の計測とサンクスページのタグ、成果承認の締切管理（放置すると自動承認）、指名検索の出稿禁止の申し入れ、成果の照合（台帳の入金と突き合わせ）。
オーナーが持つ：契約・電子署名・費用に関わる判断・メール送信（info@ から）。**先方からのメールは info@ に届くので、計測担当は転送の仕組みを整えること。**

## 5. CMOの点検と巡回

CMOは2つの周期で掲示板を見る。**依頼を出したら、最長でも1時間で返事か「受け取った」が返る。**

| 周期 | 中身 | トリガー |
|---|---|---|
| **毎時**（毎時42分） | `読む cmo` で自分あてを見て、その場で決められるものは決めて返す。調査が要るものは「受け取った、9:30で答える」と返す。返信待ちで止まっている相手は起こす | `trig_01V94sJkoyZMRdNMnB3iEXen`（予約フォームの毎時更新と同じ起動） |
| **毎日 9:30** | 下記の巡回。全スレッドの現況、深掘りが要る依頼、オーナーに上げるものの取りまとめ | `trig_01394P1gJt4SAC8ymkyDjqsU` |

オーナーの案（9/11）で毎時の点検を追加した。

**毎日 9:30（JST）の巡回**では次を行う。

- 掲示板と全スレッドの現況を見る
- 決められるものはその場で決めて返す
- スレッドをまたぐ調整はCMOが割り振る
- 止まっているスレッドは、CMOがトリガーで起こす
  （`create_trigger` に相手の `persistent_session_id` と数分後の `run_once_at`。
   用件とその場で実行できる形の指示を書くこと。「進捗どう？」では動かない）
- **オーナーに要るものだけ、1回にまとめて上げる。** 無ければ黙って終わる

## 6. 止まっているスレッドの起こし方

スレッドは、声をかけられるまで動かない。放っておくと止まったままになる。
CMOが起こす。セッションIDは `docs/org/roles/<役割ID>.md` の表にある。

## ⚠️ 別会社のものを混ぜない

`hitokachi-forms/` と `claude/auto-form-generation-system-uwv3mf` ブランチは
**ヒトカチ株式会社**のもの。この組織には入らない。
ワンヒッターの売上・顧客・報酬の情報を、そちらに持ち込まないこと。逆も同じ。
