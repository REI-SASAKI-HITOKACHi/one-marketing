## 1. いちばん大事な問題

**「決済完了」を成果地点にすると、成果タグをサンクスページに置いても正しく動きません。**

```
クリック → 申込 → サンクスページ → 現地で見積確定 → 施工 → 入金確認
                    ↑                                    ↑
              タグが打てるのはここ              でも成果はここ（2〜4週間後）
```

サンクスページは「申込を受理した瞬間」です。その時点では、

- 金額が確定していません（現地で変わります）
- 施工が終わっていません
- 入金されていません
- **そもそも成約するかも分かりません**

**ここでそのまま成果を確定させると、キャンセルにも3,000円を払うことになります。**

## 3. 注文IDの受け渡し（★ どちらの形でも必要）

先方の資料（同 p5・p7）に「顧客備考」という欄があります。
**成果と自社の記録を突き合わせるための文字列**です。

> **設定しない場合は「売上日時」での突合になり、承認作業が一気に重くなります。**

日時だけで突き合わせると、同じ日に複数の申込があったときに区別できません。

### 渡すIDの案

```
OH-<日付>-<入口>-<連番>       例）OH-20260911-mizu-003
```

| 部分 | 中身 | なぜ |
|---|---|---|
| `OH-` | 固定 | 他社の番号と混ざらない |
| 日付 | `YYYYMMDD` | 目で見て分かる |
| 入口 | `mizu` / `aircon` / `booking` | **どのフォームから来たか** |
| 連番 | 3桁 | 同日に複数あっても区別できる |

### どこで作るか

**掲載先は `/mizumawari/` の1本だけ**なので、当面はそのLPのフォームだけで足ります。

- LPのフォームは **Netlify Forms** が受けています
- **送信時に一意のIDを作って hidden 欄に入れ、同じ値を成果タグにも渡す**形になります
- 実装は `tracking/events.js` に足せます。**LPの本文には触れません**

> **ID生成の実装は、先方のタグの仕様が分かってからにします。**
> タグが「特定の変数に値を入れる」形なのか「URLパラメータで渡す」形なのかで、作りが変わるためです。

---

### ✅ 実装した中身（2026-09-11）

**注文IDの形**

```
OH-20260911-mizumawari-KY3R
└┬┘ └──┬──┘ └────┬───┘ └┬┘
 │     │        │      └ 取り違えにくい文字だけ4桁（I・O・0・1 は使わない）
 │     │        └ どのLPか
 │     └ 申し込まれた日
 └ 当社の印
```

英数字とハイフンだけなので、**URLエンコードしても文字数が増えません**
（先方の上限500文字に対して27文字）。

**どこで作って、どう渡すか**

| | すること | なぜ |
|---|---|---|
| LP（`/mizumawari/`） | 送信ボタンが押された瞬間にIDを作り、①フォームの隠し欄 `order_id` と ②`sessionStorage` の両方に入れる | ①は**Netlify Formsの受信メールに残る**ので、当社側の記録になる。②はサンクスページへ渡すため |
| サンクスページ | `sessionStorage` から読んで `_rt.cinfo` に入れ、**読んだら消す** | 消さないと、画面を読み込み直すたびに成果が立つ |

**空の成果を立てない作り**

`sessionStorage` にIDが無いときは、**タグを発火させません。**
サンクスページのURLを直接開かれた場合や、ブックマークから来た場合に、
申込が無いのに成果が立つのを防ぐためです。
先方の却下条件にも「重複」が入っているので、こちらで先に止めておきます。

**確認のしかた**

```
python3 tools/build-site.py netlify     # 組み立て
python3 tools/check-tracking.py netlify # 静的なチェック（依存なし）
python3 tools/test-rentracks-tag.py     # ブラウザで実際に動かす
```

## 4. 承認作業の運用（形1を採る場合。TODO T026）

**計測の設計の一部です。** ここが回らないと、成果地点を「決済完了」にした意味が消えます。

### 決めること

| | |
|---|---|
| 誰がやるか | 承認には入金の確認が要る。**経理の情報を見られる人** |
| いつやるか | **週1回**を推奨。管理画面に「残り日数」が出るので、締切前に必ず1回は回る |
| 何を見るか | 注文リストの各件について、**台帳で入金が確認できるか** |
| どう記録するか | 承認／拒否の判断根拠を台帳に残す（あとで先方と揉めないため） |

### 手順（先方資料 p4〜9 より）

- **1件ずつ**：注文リストで承認／拒否をチェックして実行
- **まとめて**：CSVをダウンロードし、処理列に `Y`（承認）／`N`（拒否）を入れてアップロード

### ⚠️ カレンダーに固定の予定を置いてください

**「気づいたときにやる」では、必ず取りこぼします。**
自動承認の期限は管理画面にしか出ないので、**見に行かないと分かりません。**

## 5. 電話での申込が成果にならない問題

**アフィリエイトが拾えるのはWebフォームからの申込だけです。**
当社のLPは電話番号を大きく出しているので、**パートナーが送客してもお客様が電話をかけた時点で
成果が計上されません。**

パートナーから見れば「送客したのに成果が出ない案件」です。**掲載が止まる原因になります。**

### 対処の方向（未決・MTG議題#21）

| | 内容 | 計測側から見た評価 |
|---|---|---|
| 1 | アフィリエイト経由の流入では、LPの電話導線を抑える（パラメータで出し分け） | **すぐできます。**`?src=` で判定して電話ボタンを隠す実装は、いまの仕組みに足せます |
| 2 | ユニークコールで電話CVを拾い、手動で成果登録できないか先方に確認 | **先方の回答次第。**第6章で聞きます |

**1は機会損失を生みます**（電話したい人を取りこぼす）。
**2ができるなら、そちらのほうが素直です。** まず先方に聞くべきだと考えます。
