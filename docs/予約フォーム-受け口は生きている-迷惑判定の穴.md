# 予約フォームの受け口は生きている。ただし「迷惑判定」に落ちると黙って消える（2026-09-19 実測）

## きっかけ

LP担当が、**アンケートの回答が公開から2週間、1件も保存されていなかった**のを見つけた
（フォームに `action` が無く、`post()` が何も送らないまま完了画面を出していた）。

`予約_Web` タブの申込も**開設以来0件**だったので、**同じ形を疑って自分の持ち物を実測した。**

## 結論

**受け口は生きている。壊れていない。**

本番（`https://yoyaku.onehitter.jp/`）へ実際に1件POSTしたところ、Netlify に記録された。
**ただし `verified` ではなく `spam` に入った。**

| 見る場所 | 結果 |
|---|---|
| `GET /forms/{id}/submissions`（既定） | **0件** |
| `GET /forms/{id}/submissions?state=spam` | **1件**（私のテスト送信） |
| `submission_count` | **0**（迷惑ぶんを数えない） |

**私は最初「受け口が死んでいる」と判断した。それは誤りだった。**
`submission_count=0` と既定の一覧が空だったのを、受信できていない証拠として扱ってしまった。
**迷惑判定の箱を見ていなかっただけ。**

> LP担当は同じことを先に踏んでいて、自分の報告に
> 「迷惑扱いはヘッドレスで送った私の試験方法のせい。iPhone条件では通常の箱に入る」と書いていた。
> **その一文を読んでいたのに、自分の番では確かめる前に結論を出した。**

## ⚠️ ここに本当の穴がある

**Netlify は申し込みを勝手に「迷惑」へ振り分ける。振り分けられたものは既定の一覧に出てこない。**

- `tools/booking-inbox.py` は既定の一覧だけを読んでいた
- **つまり、お客様の本物が迷惑に入ったら、こちらは永久に気づかない**
- 毎時のルーティンが「申込 0件」と報告し続けるので、**無いのか、落ちたのかが区別できない**

**予約が1件消えるのは、この事業でいちばん高い損失**（平均単価 ¥52,374）。しかも気づけない。

## 直したこと（2026-09-19）

`tools/booking-inbox.py` に迷惑判定の確認を足した。

- **取り込みはしない**（自動で台帳へ入れると、本物の迷惑メールを顧客にしてしまう）
- **必ず画面に出す。** 件数・フォーム名・日時・ID・氏名を並べ、人が見る導線を書く
- 本物だった場合の直し方も出す：Netlify 管理画面 → Forms → 対象フォーム → Spam →
  **「Mark as not spam」**。次回このツールが拾う

```
🔴 迷惑判定に 1件あります。**自動では取り込みません。人が見てください。**
   - yoyaku 2026-09-19T05:44 6aae2152bb20373c69082aca 氏名=テスト（CMO受け口確認 9/19）
```

## 広告を始める前に間に合った

**検索広告の着地は LP（`/aircon/` `/mizumawari/`）で、申込は LP のフォーム（`reserve-aircon` / `reserve-mizumawari`）が受ける。**
これも同じ経路なので、**同じ穴がある。**`booking-inbox.py` は LP のフォームも見ているので、今回の修正で両方カバーされた。

**広告で来たお客様の1件目が迷惑に入って消える、という事故は防げる形になった。**
