## 何を見せるか（壁打ち01 C-1 の「要る」だけ）

| 画面 | 見せどころ |
|---|---|
| 案件 | 請求額・元請け手取り・施工額・取り分率と**入金予定・支払予定**が**全員に見える**。手を挙げる前に入金スケジュール（下請け領収なら「領収後5日以内に支払う」）と名乗りへの同意が要る。バーで施工者／元請けの割合を表示。自分の最低受け額未満は薄く表示 |
| 協力依頼（旧「出す」） | **見積書をアップロード**（画像は文字を読み取って明細に入れる。PDFは添付のみ。見積書は成立相手だけに表示）。**明細は見積書の形**（メニュー／単価／台数／小計、行の追加、「その他」で自由入力）。単価は自社設定から自動、案件ごとに書き換え可。合計が請求額に自動で入る。**入金スケジュールが必須**（元請けが領収／下請けが現場で領収、お客様からの入金予定日、下請けへの支払予定日＝＋5日）。メニューを選ぶと料金マスターで請求額が自動計算（1箇所目は単体、2箇所目以降は同時施工、繁忙期は1台+3,300）。外部手数料（なし／20%／35%）を選ぶと**手取り**に率が掛かる。施工額の既定値は手取り×既定率、変えてよい。お客様情報は「成立した相手だけ」の枠 |
| 依頼案件一覧（旧「自分」） | 出した依頼に手が挙がると「○○に決める」。決めると相手にだけお客様情報が開く。支払予定日に双方へ通知が届く前提で、**元請け・下請けがそれぞれチェックして「本案件をクローズする」**。双方押下で完了し、相場と票の重みに反映。片方だけだと「相手のクローズ待ち（毎日催促）」。完了した案件は当事者だけに**請求書（PDF保存）**ボタン |
| 会員 | 受けた数＋出した数＝票の重み。保険・インボイス・稼働可能人数・対応メニュー・最低単価・保有設備。保険未登録は受注不可 |
| 自社設定（ヘッダーの⚙） | 稼働可能人数、保有設備、**自社料金表**（メニューごとに対応／単価／最低単価。メニューの追加可）。単価は協力依頼の明細に自動反映、最低単価は受ける案件の下限（下回る案件は薄く表示） |
| 相場 | 成立案件の中央値（手取り・施工額・取り分率）を自動表示。既存仲介の取り分と並べる |
| ルール | 開示の3層・値決め・名乗り・事故責任・受注停止基準・運営の権限・お金・決め方。**単価モデル（提示型／率／固定）と既定率（50/60/70%）をその場で切り替えられる**＝壁打ちの道具 |

## 複数社への分割依頼（2026-09-26 追加・同日オーナー指摘で改訂）

大型案件（業務用エアコン50台など。1社あたり4〜10台/日なので4〜6社が必要）を、1件の依頼で複数社に分けられるようにした。
**改訂：出す側の「分ける台数」欄は廃止（分かりにくいとの指摘）。「複数社に分ける」を押すだけにし、受ける側が台数を申告する。応募の合計台数を全員に見せる。**

| 場面 | 動き |
|---|---|
| 協力依頼 | 「依頼の仕方」で **1社に任せる／複数社に分ける** を押すだけ。必要台数は明細の最大台数から自動（2台以上のときに使える）。**施工日は複数日を1日ずつ、または期間で追加**（期間は毎日が入り、作業しない日は✕で外す。最大62日）。集金は元請けのみ（現場領収は選べない） |
| 案件（全員） | 「複数社で分担」の印。**必要台数・応募の合計台数（社数）・決定台数**と、応募と決定の2段のバー。「応募はあと○台足りません」。応募した各社の申告台数・来られる日・決定／応募中が並ぶ |
| 手を挙げる | **来られる日**（複数日の案件のみ）と **対応できる台数** を入れる。台数の初期値は「1日に対応できる台数（自社設定）×来られる日数」、残り台数が上限。台数×1台あたりの施工額をその場で表示 |
| 依頼案件一覧（出す側） | 手を挙げた会社ごとに台数を入れて「この台数で決める」（上限は申告台数と残り台数の小さい方。来られる日は申告を引き継ぐ）。**決めた会社から順に** お客様情報が開く。全台数が埋まると自動で締め切り。集まりきらないときは「募集を締め切る（残りは自社で対応）」 |
| お金 | 会社ごとの施工額＝1台あたり×台数。全台数が埋まる最後の割り当てで端数を吸収し、合計が施工額と一致する |
| クローズ・請求書・評価 | **会社ごと**。元請けは全社ぶん、下請けは自分の分だけクローズ。全社そろって案件完了。請求書は施工日に来た日を載せ「○台のうち△台分」。保存期限は最終日から60日。支払遅延の申し送りは全社に届き、遅延は案件1件として数える |
| 会員・自社設定 | 自社設定に「1日に対応できる台数」を追加。会員一覧にも表示 |

データ：案件の施工者は `assign`（会社ごとの台数・来る日・施工額・クローズ・評価）、申告は `offers`（台数・来られる日）、複数日は `dates`。旧データは読み込み時に自動で移す（`accepted`→`assign`、数値だけの申告→台数＋日）。
架空データ：「業務用エアコン×50・5日間（運営会社が出し、協力店Bに10台で決定済み、C店6台・A店4台が応募中）」と「×20・飛び飛び2日（協力店Cが出し、B店8台が応募中）」。
確認：Chromium の自動操作で29項目（手を挙げる→台数を決める→決まった会社だけに情報→締め切り→全社クローズ→会社ごとの請求書、複数日・期間での依頼、1社の案件、旧データの移行）。

## 試用版の公開（2026-09-26 オーナー指示）

**URL：https://kyoryokuten-net-demo.netlify.app/** （Netlify の専用サイト `kyoryokuten-net-demo`。LPのサイトとは別。配信は `python3 tools/build-network-demo.py && python3 tools/deploy-network-demo.py`）

同業者に触ってもらうため、デモ状態のまま公開する。データは**開いた端末の中だけ**に保存（共有されない）。検索エンジンには載せない（noindex）。
公開版では会員名「ワンヒッター」を「運営会社」に、相場ページの既存仲介の名前（FC名・サービス名）を一般名に変えた（配布資料と同じ方針）。

## 操作の流れ（9/26 の見せ方）

1. 「操作中」を **ワンヒッター** にして「出す」→ エアコン2台＋防カビ、江戸川区、日付 → 請求額と施工額が自動で出る → 募集
2. 「操作中」を **協力店A** に切り替え → 「案件」でその案件に手を挙げる
3. **ワンヒッター** に戻す → 「自分」→ 協力店A に決める → 協力店A に切り替えると、お客様情報が見える
4. 「相場」で中央値、「ルール」で権限と利用料を見せる
5. 「ルール」で既定率を 70% にしてから「出す」に戻ると既定値が変わる（単価の議論用）

## 見積書の読み取り（OCR）について

- デモは Tesseract.js（ブラウザ内で動く文字認識、日本語データ）を使う。**初回は数十秒の読み込みがある**。通信できる環境が要る
- 読み取った文字から、メニュー名のキーワード（エアコン／浴室／レンジフード…）と台数・金額を拾って明細に入れる。**精度は写真の質に依存し、必ず目で確認する前提**
- この実行環境からは外部通信ができないため、**OCR本体の動作は未確認**。解析部分（文字→明細）だけ確認済み
- 本番は、画像をサーバー側で読み取る方式（Claude API の画像入力など）に置き換えると精度が上がる。費用は別途

## 2台で見せたいとき

`tools/network-api.gs` をスプレッドシートの Apps Script に貼ってウェブアプリで公開し、
`python3 tools/build-network-demo.py --api <execのURL>` で作り直す。
同じデータを複数端末で共有できる。デモ用の簡易な作り（後勝ち保存）なので本番設計ではない。

## 架空データについて

会員名（協力店A〜D）、お客様名、金額はすべて架空。実在の会社・人物ではない。
石田君・かくらい君の名前は入れていない（本人の前で見せる資料なので、勝手に載せない）。

## 本番で作り直すときに変わること

- 会員ごとのログイン（LINEログインが有力。会員は全員LINEを使っている前提）
- データベース（Firestore か Supabase）。1セルJSONではない
- 通知（案件が出たら条件に合う会員にLINE通知、手が挙がったら出した人に通知）
- 判定の自動化（受注停止基準）、判定ログ、エクスポート
- 首かけカードの発行（会員ごとのQR）
